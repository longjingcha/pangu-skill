# 盘古提炼协议规范

> 从原始材料到可运行协议：人物协议、领域协议与开天能力的统一标准

---

## 0. 目标

本规范定义三件事：

1. 如何把原始材料提炼成**人物协议**
2. 如何把原始材料提炼成**领域协议**
3. 当原问题本身失真时，如何触发**开天能力**，先重构问题，再继续生成

**总原则**：不是把信息写得更多，而是把对象变成可调用、可判断、可验证的协议。

---

## 1. 术语约定

| 术语 | 统一含义 |
|------|---------|
| 人物协议 | 面向具体人物的思维、规则、表达与边界规范 |
| 领域协议 | 面向专业领域、方法论、主题、学科的知识与判断规范 |
| 模型 | 可跨场景复用的稳定认知结构 |
| 规则 | 可执行、可重复的判断动作 |
| 表达规则 | 输出风格、句式、措辞、节奏、禁忌词 |
| 知识协议 | 领域的结构化表达，含边界、结构、判断、路径、失效条件 |
| 开天能力 | 对错误问题、伪前提、失真边界的重构能力 |
| 生成流程 | 采集、提炼、验证、构建、交付的完整流水线 |

---

## 2. 输入类型判定

生成前先判断输入属于哪类对象：

| 输入类型 | 默认产物 | 说明 |
|---------|---------|------|
| 明确人物 | 人物协议 | 具体人名、英文名、别名 |
| 明确领域/主题/方法论 | 领域协议 | 如价值投资、增长、产品设计、写作 |
| 混合输入 | 先判定主目标 | 若既像人物又像领域，先确认用户更需要哪一种 |
| 模糊目标/困惑 | 开天判断 + 再分流 | 先判断问题是否要重写，再决定走人物还是领域 |

**分流规则**
- 如果用户要的是“像某个人那样想”，走人物协议
- 如果用户要的是“这个领域怎么学、怎么判、怎么做”，走领域协议
- 如果用户问的是“问题本身是不是错了”，先触发开天能力

---

## 3. 开天能力

当问题满足以下任一条件，先不开人物或领域协议，先重构问题：

- 目标与手段混在一起
- 只是在问表面症状，不是根因
- 问题过宽，无法落到判断或行动
- 问题默认前提明显可疑
- 用户真正需要的是换一个问题

### 3.1 开天输出

开天输出必须包含三部分：

1. **问题诊断**：为什么当前问题不适合直接回答
2. **问题重写**：把原问题改写成更可回答的版本
3. **后续分流**：重写后应走人物协议还是领域协议

### 3.2 开天触发词

以下词语或语义接近表达都应视为开天信号：
- 重写问题
- 重构
- 伪问题
- 伪前提
- 边界不清
- 表面症状
- 问题本身
- 开天

---

## 4. 人物协议提炼规范

人物协议要抽取的是“稳定可复用的思维结构”，不是语录拼接。

### 4.1 三重验证

一个候选观点要进入人物协议中的**模型**，必须同时满足：

1. **跨域复现**：在至少 2 个不同场景/领域出现
2. **有生成力**：能推断其对新问题的立场
3. **有排他性**：不是所有聪明人都会这样想

### 4.2 判定规则

- 3/3 通过 → 进入模型
- 1/3 或 2/3 通过 → 降级为规则
- 0/3 通过 → 丢弃

### 4.3 人物协议字段

| 字段 | 含义 | 必填 |
|------|------|------|
| models | 稳定认知结构 | 是 |
| rules | 可执行判断动作 | 是 |
| expression_rules | 输出风格与措辞偏好 | 是 |
| timeline | 关键时间线 | 是 |
| values | 价值观与反模式 | 是 |
| tensions | 内在张力 | 是 |
| boundary | 诚实边界 | 是 |
| sources | 调研来源 | 是 |

### 4.4 人物协议输出要求

- 先模型，再规则
- 先规则，再风格
- 先边界，再叙述
- 先局限，再交付
- 不伪装成百科总结
- 不把观点写成口号

---

## 5. 领域协议提炼规范

领域协议要抽取的是“可执行的知识协议”，不是专业术语堆叠。

### 5.1 领域协议的四层结构

| 层级 | 目标 | 最低输出 |
|------|------|----------|
| L1 边界层 | 先知道领域是什么、不是什麼 | scope、子域、前提 |
| L2 结构层 | 先知道怎么拆 | core_map、模块关系 |
| L3 判断层 | 先知道怎么判对错 | criteria、反例、失效条件 |
| L4 行动层 | 先知道怎么做 | path、decision_actions |

### 5.2 领域协议字段

| 字段 | 含义 | 必填 |
|------|------|------|
| scope | 领域边界与子域 | 是 |
| core_map | 核心结构与关系 | 是 |
| criteria | 判断标准与评价口径 | 是 |
| path | 最短可行路径 | 是 |
| pitfalls | 典型误区 | 是 |
| counterexamples | 反例 | 是 |
| failure_modes | 失效条件 | 是 |
| schools | 流派分歧 | 视情况 |
| progression | 进阶路径 | 视情况 |
| decision_actions | 可执行动作 | 是 |

### 5.3 领域协议输出要求

- 先边界，再结构
- 先标准，再案例
- 先失效条件，再适用条件
- 先反例，再正例
- 先最小路径，再完整路径
- 先共识，再分歧，再使用场景
- 先判断动作，再解释原因

### 5.4 领域协议内容约束

领域协议中不得只给抽象定义，必须至少覆盖：
- 这个领域怎么拆
- 怎么判断对错
- 怎么入门
- 怎么避坑
- 什么情况下要停手或切换方法

## 6. 表达规则提炼

表达规则用于描述输出风格，不用于替代内容结构。

### 6.1 句式指纹

记录以下特征：
- 平均句长
- 疑问句比例
- 类比密度
- 第一人称频率
- 确定性语气比例
- 转折频率

### 6.2 风格轴

| 轴 | 两端 |
|------|------|
| 正式度 | 正式 ←→ 口语 |
| 抽象度 | 抽象 ←→ 具体 |
| 谨慎度 | 谨慎 ←→ 断言 |
| 节奏 | 铺垫型 ←→ 结论先行 |
| 叙述方式 | 数据驱动 ←→ 叙事驱动 |

### 6.3 禁忌词与口癖

- 明确不用的词：禁止在输出中复用
- 高频词：可以保留，但避免表演化复读

---

## 7. 矛盾处理原则

矛盾是结构的一部分，不是错误。

### 7.1 时间性矛盾
- 早期说 A，后期说 B
- 处理：标注演化轨迹，默认以近期为主

### 7.2 场景性矛盾
- 不同场景采用不同规则
- 处理：按场景分别记录，不强行统一

### 7.3 本质性张力
- 同时成立但彼此冲突的价值
- 处理：显式记录为核心张力

**禁止做法**
- 选一边忽略另一边
- 编造调和解释
- 假装矛盾不存在

---

## 8. 信息不足时的处理

| 情况 | 处理 |
|------|------|
| 公开信息很少 | 标注为推测，不伪装为事实 |
| 只有二手信息 | 降低置信度，明确来源 |
| 信息矛盾且无法判断 | 并列呈现，不强行裁决 |
| 对方保持沉默 | 尊重边界，标注不可知 |

---

## 9. 调研与生成流程

### 9.1 采集
按对象类型收集可验证材料：
- 人物：著作、访谈、表达、他者评价、决策记录、时间线
- 领域：定义、教材、论文、标准、实战案例、流派资料、反例

### 9.2 提炼
- 人物：models、rules、expression_rules、boundary
- 领域：scope、core_map、criteria、path、pitfalls、counterexamples、failure_modes、schools、progression、decision_actions

### 9.3 验证
- 人物：用已知问题做一致性测试
- 领域：用真实任务做可执行性测试
- 开天：用重写后的问题验证是否更适合继续生成

## 10. 质量自检清单

### 10.1 人物协议
- [ ] 模型是否 3-7 个？
- [ ] 每个模型是否有跨域证据？
- [ ] 是否有明确局限？
- [ ] 表达规则是否有辨识度？
- [ ] 是否保留了真实张力？
- [ ] 是否明确写出做不到什么？

### 10.2 领域协议
- [ ] `scope` 是否清晰？
- [ ] `core_map` 是否能快速建立结构感？
- [ ] `criteria` 是否可用于判断对错？
- [ ] `path` 是否可执行？
- [ ] `pitfalls` 与 `counterexamples` 是否真实？
- [ ] `failure_modes` 是否明确？
- [ ] `schools` 是否保留分歧？
- [ ] `decision_actions` 是否能落到行动？

### 10.3 开天判断
- [ ] 是否识别了伪前提或边界不清？
- [ ] 是否给出了重写后的问题？
- [ ] 是否说明应走人物协议还是领域协议？

### 10.4 整体
- [ ] 删除对象名后，仍能识别其协议特征？
- [ ] 输出不是原话拼接，而是协议运行结果？
- [ ] 新问题能被协议处理，而不是只会复述旧案例？
